# ADR 0016: Custom Agents and Scoped Bounty HTTP

Gospel gains user-authored custom agents alongside the built-in roles. An Agent Definition is an `AGENT.md` under `<workspace>/.agents/agents/<name>/` (or `~/.agents/agents/<name>/` globally) with YAML frontmatter — required `name` and `description`, optional `tools`, `skills`, `model`, `worker_model`, `max_turns`, `deadline_seconds`, and `network` — plus a markdown body that becomes the agent's own preamble section. Discovery mirrors skill discovery: workspace definitions override global ones, folder name must match the frontmatter name, and results are cached behind the agent loader.

A session may carry a selected agent (`session_agents.agent_id`, exposed on session records and details through a LEFT JOIN). Switching agents mid-session keeps the session's model and Model History untouched; only the Harness Profile changes. Selection persists across reload, fork, and archive/restore. When a custom agent is active the Session Turn resolves its definition into an `AgentRole::Custom` Harness Profile: the declared tool names resolve against a fixed allowlist (read-only workspace tools plus `write_harness_file`), attached skills become a preamble section, and `max_turns`/`deadline_seconds` become the run guards. Custom agents never receive shell, git, or GitHub CLI tools, regardless of what the definition lists.

A leading `@agent <task>` message instead runs one bounded delegated sub-turn before the main stream: the named agent runs with its own profile (and its `model` if declared, else the session model), its report is injected into the main prompt as a `## Delegated report` section, and synthetic `delegate_agent` tool call/result events render the delegation as a normal activity card. Unknown agent names inject a failure note rather than aborting the turn. Delegated agents require an active workspace.

`network: true` unlocks exactly one network route: the `http_request` tool backed by `BountyHttpTool`. It is the only way a custom agent can reach the network — no shell, no `curl`, no browser. Every request is checked against `.gospel/bounty/scope.yaml` (or `scope.yml`) in the workspace before it is sent: the file must exist, parse, set `authorized: true`, and declare at least one `in_scope` rule. Host (with `*.` wildcard), path glob, method, and port rules are matched; `out_of_scope` rules win; mutating methods need `allow_mutations: true`; plain HTTP needs `allow_http: true`; private and localhost hosts need `allow_private_hosts: true`. A missing or invalid scope file is a hard deny, not a warning.

The tool enforces a per-host rate limit, a 30 s default timeout (per-request override capped at 60 s), and a 1 MiB default response cap. When `follow_redirects: true`, redirects are followed manually hop-by-hop (cap 5): each `Location` target re-passes `decide()` with the method it will actually be sent with (303/301/302 from non-GET downgrade to GET and drop the body), `Authorization`/`Cookie` headers are stripped on host changes, and a denied hop returns the 3xx response with the refusal recorded in `redirects` and the audit log. Named `auth_profiles` resolve secrets from `env:` or `keychain:` references at request time (`keychain:` reads the app credential store under a `bounty.` namespace, populated by the `store_bounty_secret` command); the raw secret never enters prompts, tool output, evidence, or audit logs. `Authorization`, `Cookie`, `Set-Cookie`, and token-shaped body fields are redacted. Each run writes redacted request/response evidence under `.gospel/bounty/runs/<run-id>/evidence/` and an audit line to `requests.jsonl`.

`bounty_surface` is the recon extractor: it sends one GET through the same scoped pipeline (scope, checkpoint freeze, rate limit, redirect chain, evidence) and parses the redacted response body into title, links, forms (method/action/inputs), and script URLs — each link and form action tagged `in_scope` so the agent sees which discovered endpoints are actually testable. There is deliberately no JavaScript engine: a page the target renders client-side shows as sparse rather than executing untrusted markup, and scope can never be escaped by a subresource fetch.

Network-enabled agents can also record typed signals through `record_bounty_signal`. A signal carries a `kind` from the fixed hypothesis taxonomy (`enforcement_gap`, `inconsistent_enforcement`, `unchecked_assumption`, `undocumented_dependency`, `composition_vulnerability`, `inconsistent_access_path`, `identity_rebinding`, `failed_request_side_effect`, `ordering_dependency`, `partial_rollback_side_effect`, `post_delete_access`, `unauthorized_state_reversal`, `contradictory_state`, `other`), an endpoint, a summary, linked `evidence_ids`, `confidence`, `status`, and an optional `hypothesis`. Signals append to `.gospel/bounty/runs/<run-id>/signals.jsonl` and deduplicate deterministically on (kind, method, normalized endpoint) so repeated observations return the existing signal id instead of growing the file. Typed signals — not free-form markdown — are the contract the future mutator, dedup, and frontier-triage stages consume.

An Agent Definition may also set `orchestration: sweep`, which turns `@agent` delegation into a deterministic pipeline the orchestrator — not the model — drives. Selecting an orchestrated agent at session level makes every prompt an implicit delegation: the pipeline runs, its report is injected into the turn, and the session model presents it; orchestrated agents never resolve a conversational Harness Profile. A sweep runs five fixed phases: a scope gate that refuses before any model call without an authorized `scope.yaml`; a mutator on the lead model that emits a capped JSON hypothesis set from scope + task + `recon.md`/`threat-model.md` + prior signals and hypotheses; a worker fan-out where each hypothesis becomes one bounded worker turn on `worker_model` (4 concurrent, ≤12 turns, 5-minute deadline, tools narrowed to `read_file`/`http_request`/`record_bounty_signal`); up to two feedback rounds that mutate follow-up hypotheses only when a round produced new signals; and a lead-model triage that classifies every signal `confirmed`/`rejected`/`needs_review` and writes `triage.jsonl` plus `sweep-report.md`. Worker outcome never branches the loop on its own — only new signals do. `model` routes the lead (mutator/triage), `worker_model` routes workers, and either falls back to the session model. This completes the `worker_model` wiring.

The built-in `bug-bounty` agent (`.agents/agents/bug-bounty/AGENT.md`) ships with four methodology skills (`bounty-recon`, `bounty-authz`, `bounty-logic`, `bounty-report`) and `network: true`. Its workflow requires recon and a human checkpoint before broad testing. `bug-bounty-sweep` (`orchestration: sweep`) runs the swarm above. A findings surface (`Bounty findings` in the command palette) lists a run's signals merged with triage verdicts plus the sweep report via `list_bounty_findings`, with a run picker and per-signal verdict buttons (`set_bounty_verdict` appends a `source: "user"` verdict line; latest verdict wins). The recon→testing boundary is capability-enforced: the network-gated `bounty_checkpoint` tool writes `threat-model.md` plus a `checkpoint.pending` marker, and `BountyHttpTool` refuses every request while the marker is pending; `approve_bounty_checkpoint` (panel button) writes `checkpoint.approved`. One caveat: the gate only engages once the agent calls `bounty_checkpoint` — whether it calls remains prompt-driven. Full browser automation (JS execution, click/keyboard, subresource fetching under interception) is deliberately out of this slice — `bounty_surface` covers static recon without running untrusted markup.
